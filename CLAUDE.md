# MARC-from-LARC

Automated pipeline for generating and verifying MARC (Metaphor Abstraction and Reasoning Corpus) puzzles. Tests whether figurative language + examples together enable puzzle-solving that neither achieves alone.


## Data Sources

### LARC Tasks (task_id 0-399, source='larc')
- 400 ARC tasks with human-authored literal descriptions (see/do/grid)
- Figurative descriptions generated by Claude Agent subagents (generator_model='claude-agent')

### MARC Submissions (task_id 1000-1176, source='marc-submission')
- 177 hand-crafted puzzles with human-authored metaphors (generator_model='human')
- Loaded via `python load_marc_submissions.py`
- Normalized JSON (integer cells) written to `data/marc-submissions/`
- Single metaphor field (no see/do/grid split) -> uses unified prompt in prompts.py
- 1-5 training examples (mode: 2), always 1 test case with output

## Database Schema -- Key Tables

### `figurative_descriptions` (critical for mech-interp work)

Each MARC puzzle can have **multiple figurative descriptions** (variants) from different source domains:

```sql
figurative_descriptions (
    fig_id           INTEGER PRIMARY KEY,
    task_id          INTEGER REFERENCES tasks(task_id),
    generator_model  TEXT,     -- 'claude-agent' (LARC) or 'human' (submissions)
    variant          TEXT,     -- 'original', 'alt-1', 'alt-2', ...
    source_domain    TEXT,     -- 'biology', 'warfare', 'cooking', etc. (NULL for originals)
    metaphor         TEXT,     -- the figurative clue
    figurative_see   TEXT,     -- empty for single-metaphor variants
    figurative_do    TEXT,
    figurative_grid  TEXT,
    UNIQUE(task_id, generator_model, variant)
)
```

**Querying variants:**
- `get_all_variants(conn, task_id)` -- returns all variants for a task, **original first**, then alt-1, alt-2, etc.
- `get_figurative(conn, task_id, generator_model, variant='original')` -- get a specific variant
- To check if a variant preserves MARC property, query `figurative_trials` for that `fig_id`

**How variants relate to trials:** Each variant has its own `fig_id`. The `figurative_trials` table links to `fig_id`, so every trial (k=0 through k=num_train) is per-variant. To compare how two metaphors led to different reasoning on the same puzzle, join `figurative_trials` on `fig_id` and compare `reasoning` columns.

### Other tables
- `tasks` -- 577 rows (400 LARC + 177 submissions), distinguished by `source` column
- `baseline_trials` -- examples_only / language_only / both results
- `task_subsets` -- classification (examples_sufficient, language_sufficient, etc.)
- `figurative_trials` -- per-variant, per-model, per-k trial results with reasoning traces

## Pipeline Phases

1. **Collect** (`collect.py --concurrency 8`): Two-pass LLM testing under 3 conditions x all training examples
2. **Subset** (`subset.py`): Classify into examples_sufficient / language_sufficient / both_required / unsolvable
3. **Generate Figurative** (`generate_figurative.py`): Create metaphorical descriptions via Claude Agent subagents
4. **Test Figurative** (`test_figurative.py --concurrency 8`): Test at k=0,1,...,num_train; verify MARC property
4b. **Alternative Clues** (`generate_alternatives.py`): Generate domain-diverse alternative metaphors, verify MARC property
5. **Analyze** (`analyze.py`): Generate report.html with charts and statistics

For MARC submissions, skip phases 2-3 (no literal descriptions; metaphors already exist). Run:
- `collect.py --condition examples_only --source marc-submission` for baseline
- `subset.py classify-marc-submissions` for classification
- `test_figurative.py test --generator-model human --source marc-submission --concurrency 8` for figurative testing
- `test_figurative.py verify-marc --generator-model human --source marc-submission` for MARC verification

### Alternative Figurative Clues (Phase 4b)

Each MARC-verified puzzle gets multiple figurative clues from different source domains, enabling mechanistic interpretability comparisons (same puzzle, same examples, different metaphor -> different reasoning path).

**Generation:** Done by Claude Code Agent subagents (not API scripts). Alternatives are inserted via:
```bash
python generate_alternatives.py insert-batch --json-file alternatives.json
```

**Verification:** Tests each alternative at k=0,...,num_train. Always use `--concurrency 8`:
```bash
python generate_alternatives.py verify --model gpt-oss-120b --concurrency 8
python generate_alternatives.py verify --model gpt-oss-20b --concurrency 8
```

**Reporting:**
```bash
python generate_alternatives.py report --model gpt-oss-120b
python generate_alternatives.py report --model gpt-oss-20b
```

## Inspector Views

Two HTML views generated by `inspector.py`:

```bash
python inspector.py inspect --output inspect.html   # Main tabbed inspector
python inspector.py compare --output compare.html   # Variant comparison view
```

**`inspect.html`** -- Main inspector with collapsible puzzle panels. Each puzzle has:
- Training examples (visual grids)
- Literal description (LARC tasks only)
- Tabbed figurative variants (original first, then alt-1, alt-2, etc.)
- Two dots per tab: first = 120b MARC status, second = 20b (green = valid, red = invalid)
- Per-variant: metaphor text, per-model badges (120b: n=k / 20b: fail), prediction grids, reasoning traces
- MARC Property section: side-by-side examples_only FAIL vs figurative+examples PASS per model
- Nav links color-coded: blue = 2+ valid 120b alts, yellow = 1, red = 0

**`compare.html`** -- Variant comparison view optimized for interpretability work:
- All variants for each puzzle stacked vertically as cards
- Per-variant: 120b and 20b results side-by-side in columns
- Each column shows prediction grid and full reasoning trace (5000 chars)
- Valid variants highlighted (green border), invalid faded (red border)

## Adding a New Model

1. Add entry to `config.yaml` (name, provider, endpoint, model_id, etc.)
2. `python collect.py --model <name> --source larc` (all 3 conditions)
3. `python collect.py --model <name> --condition examples_only --source marc-submission`
4. `python subset.py classify --model <name>` (LARC tasks)
5. `python subset.py classify-marc-submissions --model <name>` (MARC submissions)
6. `python test_figurative.py test --model <name> --generator-model claude-agent --source larc --concurrency 8`
7. `python test_figurative.py test --model <name> --generator-model human --source marc-submission --concurrency 8`
8. `python test_figurative.py verify-marc --model <name> --generator-model <gen>`
9. `python generate_alternatives.py verify --model <name> --concurrency 8`
10. `python inspector.py inspect` and `python inspector.py compare`

## Key Design Decisions

- **Two-pass LLM approach**: Pass 1 (reasoning) uses the subject model; Pass 2 (extraction) uses gpt-oss-120b regardless of subject model. This is critical -- smaller models like 20b produce ~45% parse errors when doing their own extraction, but only ~18% when 120b handles extraction. `call_llm_two_pass()` accepts an optional `extraction_model_config` parameter for this. Workers retry up to 3 times on parse error before giving up.
- **Concurrency**: Both `test_figurative.py` and `generate_alternatives.py` support `--concurrency N` using `ThreadPoolExecutor`. Each worker opens its own SQLite connection. Always use `--concurrency 8` for MindRouter batch jobs.
- **Figurative generation**: Use Claude Agent subagents (not MindRouter models). They produce structurally informative metaphors with zero parse failures.
- **MARC property**: (1) examples alone fail, (2) figurative alone fails, (3) figurative + examples succeeds for some k.
- **Unified metaphor prompt**: MARC submissions and alternative clues use `build_figurative_unified_only/with_examples()` since they have a single metaphor string, not a see/do/grid split. Dispatcher auto-selects based on whether `figurative_see` is empty.
- **Task ID scheme**: LARC 0-399, MARC submissions 1000+. Distinguished by `source` column in `tasks` table.
- **Variant storage**: Multiple figurative descriptions per task via `variant` column ('original', 'alt-1', ...) and `source_domain` column. Unique key is `(task_id, generator_model, variant)`.

## LLM Infrastructure

- **MindRouter** (University of Idaho HPC): OpenAI-compatible endpoint at `https://mindrouter.uidaho.edu/v1`
- API key env var: `MINDROUTER_API_KEY`
- Reasoning models (gpt-oss-*) put output in `reasoning_content` with null `content`
- Vision models: qwen3-vl-32b and qwen3.5-400b (both accept image content blocks)

**IMPORTANT -- Parallelism:** MindRouter easily handles 8+ concurrent API calls. Always use `--concurrency 8` (or higher) when running batch jobs. Sequential execution wastes hours. Both `test_figurative.py` and `generate_alternatives.py` have the ThreadPoolExecutor pattern built in.

**IMPORTANT -- Extraction model:** When testing smaller models (20b, etc.), always use 120b for the extraction pass. This is handled automatically by `get_extraction_model_config()` in `utils.py`. If you add a new model, make sure this function returns the 120b config for it.

## Vision Pipeline

Tests the MARC hypothesis with vision models by sending a single composite PNG (all grids in a vertical stack) instead of text-rendered grids. Figurative clues remain as prompt text.

**Key differences from text pipeline:**
- Single composite image instead of multiple per-grid image blocks
- Separate database (`marc_vision.db`), same schema, bootstrapped from `marc.db`
- `v_prompts.py` builds prompts with `compose_puzzle_image()` from `grids.py`
- Default `--concurrency 4` (vision models are slower)

**Running the vision pipeline:**
```bash
python v_setup.py                                     # Bootstrap marc_vision.db
python v_collect.py --model qwen3-vl-32b --source larc --concurrency 4
python v_collect.py --model qwen3-vl-32b --source marc-submission --concurrency 4
python v_subset.py --model qwen3-vl-32b
python v_test_figurative.py test --model qwen3-vl-32b --generator-model claude-agent --source larc --concurrency 4
python v_test_figurative.py test --model qwen3-vl-32b --generator-model human --source marc-submission --concurrency 4
python v_test_figurative.py verify-marc --model qwen3-vl-32b --generator-model claude-agent --source larc
python v_test_figurative.py verify-marc --model qwen3-vl-32b --generator-model human --source marc-submission
```

**Error recovery:** Network drops cause errored trials. To retry:
```bash
python -c "from db import init_db; c=init_db('marc_vision.db'); c.execute('UPDATE <table> SET error=NULL WHERE error IS NOT NULL AND response_text IS NULL'); c.commit()"
# Then re-run the same command -- it skips completed trials
```
